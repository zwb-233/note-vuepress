原理

响应式原理

  • 在React中，数据是通过useState定义的，这返回了一个修改数据的函数，在调用这个函数时，React就知道需要重新调用这个函数，从而更新虚拟和真实DOM
  • React中更新需要完整地更新变量，也就是完整替换，这方便了对比引用，快速判断变量是否被修改，得知在哪个组件函数中被修改
    • 虽然React并没有为状态变量设置不可更新标识符immutable，但对状态变量直接修改不会被记录变化，只有使用setState函数重新赋值才能触发更新
  • React并没有追求最小计算，而是简单地重新执行整个组件函数，返回新的结构。这不用追踪变量的所有情况，进行依赖收集，发布更新通知，实现最小DOM更新依赖后续的虚拟结构比较
    • 当然，这也扩展出一个问题，如何让React知道哪些子结构需要被跳过，避免无意义的更新，React 19引入了静态编译器，可以帮助将代码编译为尽可能缓存的版本(编译器playground)
    • react中有大量以use开头的缓存方法，比如useMemo、useCallback这些方法可以缓存数据，在依赖的数据没有改变时，不会重新计算数据
    • 除此之外，需要确保传入参数的指针一致，结合React.memo缓存这样能更好地知道何时子组件不需要重新渲染
      • 传入的参数应该在父组件中缓存，因为传入的内容是一个对象，每个键指向父组件的一个变量，React.memo会通过Object.is判断每个键所对应的新旧值是否相等，对于引用数据这要求指针地址相等
      • 当然也可以直接在父组件判断使用的数据是否变化，只有变化时，才重新创建节点，这也是React编译器使用的方法
  • React默认需要重跑整个组件和子组件树的构建函数，但不是里面执行，更新任务会被添加到任务堆中，等待调度更新，并批量处理

渲染机制

  • React在早期时，需要以同步递归地方式遍历虚拟DOM树，因为更新的粒度大，一旦开始渲染很容易卡死主线程，在React 16之后，出现了一种Fiber结构，目标是把渲染拆分成科中断、可恢复、可自定义优先级排序的工作单元，实现并发渲染，确保高优先级更新可以打断低优先级
  • Fiber结构，实际上是一种链表树结构，它放弃了用数组children: []连接子节点，而通过三个指针的形式将整个需要遍历的虚拟DOM树按渲染顺序链接，能够方便进行树的深度优先遍历，且能够随时暂停

    • 遍历规则

      • 有child，就往下走：如果当前节点有child，就进入child节点
      • 没child，找sibling：如果没有child了(说明到底了)，就找当前节点的sibling(亲兄弟)
      • 没sibling，找return：如果没有sibling了(说明这一层到底了)，就退回到return(父节点)，然后在父节点上继续找sibling的操作
      // 极简版的 Fiber 节点结构
const fiber = {
  // 1. 静态结构信息（我是谁）
  type: 'div',       // 或者是函数组件 App、类组件等
  key: null,         // 用于 Diff 的 key
  
  // 2. 动态状态信息（我现在的状态）
  pendingProps: {},  // 即将生效的新 props
  memoizedState: [], // 当前 hook 链表（如 useState 的值）
  
  // 3. 连接信息（也就是如何组成树的核心）
  return: parentFiber,   // 指向我的父节点
  child: firstChildFiber,// 指向我的第一个子节点
  sibling: nextFiber     // 指向我的下一个亲兄弟节点
  
  // 还有一个极其重要的隐藏属性
  alternate: anotherFiber // 指向另一棵树里跟我在同一位置的节点（双缓冲机制）
}

    • Fiber意为纤程，是比线程更小的执行单元，暂停和开启可以由程序员控制，这使得React可以在执行部分虚拟结构渲染时暂停，处理其他用户输入等任务，之后在下一帧重新恢复继续执行，确保用户体验

    • 组装新的Fiber树

      • 寻找起点：寻找当前应用的根节点，完整的结构是从根节点开始的，方便判断沿途的所有父节点是否有被跳过渲染，避免状态上下文错误
  • 在任意时刻，内存中同时存在两棵Fiber树：
    • current树(当前树)：其内部的节点直接对应屏幕上已经渲染的真实DOM，代表用户当前看到的画面
    • workInProgress树(WIP树，工作树)：当触发更新时，React在后台基于current树克隆/计算生成的新树
    • 切换瞬间：当WIP树在内存中构建完毕，且对应的DOM也拼装好后，React会在Commit阶段将根节点的current指针直接指向WIP树。此时WIP变成current，旧的current树变成废料等待回收，屏幕瞬间更新
  • 由于Fiber可中断，如果边构建边修改真实DOM，就会出现界面错乱。React将更新严格分为两个阶段：
    • Render阶段 (可中断)：纯JavaScript计算。遍历Fiber树，执行组件函数，计算状态，对比差异，仅给Fiber节点打上增删改的标签 (如Placement、Update)。此阶段绝对不操作真实DOM，即使中断一万次，用户在屏幕上看到的依然是旧的current树，画面完好无损。
    • Commit阶段 (不可中断)：只有当Render阶段完整走完，生成完整的WIP树后才会触发。此阶段无视shouldYield(不响应时间切片)，霸占主线程，一口气根据Fiber节点上的标签完成所有真实DOM的操作，保证界面一次性完整刷新。
  • Lane模型

    • Lane意为车道，实际上是任务的优先级标签

      • 一个操作可能有多个优先级标签(通过位运算|)
      • 位数越低，优先级越高(例如 SyncLane是最低位，优先级最高)

    • Lane 本身只是标签，不会直接进入调度器。在设置调度任务时优先级标签会经过转换，得到任务的过期时间

      • 提取高优先级标签的固定过期时间，加上当前页面的毫秒时间(performance.now())，转换成任务的实际到期时间，作为调度器排序的依据
      • 调度器为任务使用最小堆排序，每次输出的是优先级最小的，也就是最快过期的任务

    • 每次执行切片shouldYield前会调用markStarvedLanesAsExpired判断某一Lane是否存在过期

      • 若发现Lane的过期时间已过，这表明有任务饥饿，将Lane标注为饥饿，添加到root.expiredLanes
      • 被标注为饥饿的Lane中的最近任务在下次执行时会同步执行，不切片
      • Lane的过期时间是在切片执行前发现有Lane的过期时间expirationTime仍为NoTimestamp时根据优先级进行设置的

  • 任务安排与切换

    • 使用schedulePerformWorkUntilDeadline安排切片任务，React中添加短时间的渲染宏任务，确保任务的执行和可打断
      • localSetImmediate：原生的setImmediate功能，在Nodejs(事件循环check阶段，延迟最低)和IE(IE最快宏任务)中可用
      • MessageChannel：几乎零延迟，非常可靠的浏览器宏任务
      • setTimeout(0)：有4ms延迟，但所有环境都支持
    • 对应的任务执行函数performWorkUntilDeadline在执行完成时如果有任务未完成，接着调用schedulePerformWorkUntilDeadline，继续安排下一次切片任务
    • 相关特性
      • Update队列合并：同一个组件高频触发的多次setState，不会产生多次构建，而是以单向循环链表的形式挂在该组件的Fiber节点上，等构建走到该节点时一次性消费，将对同一个值的操作合并为一次从Root开始的构建
      • 高优打断与“拔管”：如果低优任务(如长列表渲染)正在构建WIP树，此时来了高优任务(如输入框onChange)，调度器会通过cancelCallback直接将低优任务从最小堆中踢出队列(拔管)，优先构建高优任务
      • 作废旧进度：高优任务基于最新的current树重新从Root开始构建并上屏，当然大部分节点是可以复用的。上屏后，React发现被踢掉的低优任务基于的旧状态已经冲突过期，会直接丢弃其算了一半的WIP树，等空闲时基于高优产生的新状态，重新发起一次低优构建
      • 防饥饿机制：如果低优任务一直被高优任务打断(例如用户疯狂拖拽滑块)，低优任务等待时间超过其“绝对死线”，会被强行提拔为同步最高优先级，无视时间切片一口气渲染完成，防止长时间无法上屏
      • 当低优任务被高优打断，后又被重新调度时，它并不是“瞬移”到之前断开的节点继续算。而是重新从Root开始跑while循环，但因为之前未改变分支的节点指针(child、sibling)早已连好，它会极速滑过这些已完成的节点，直到滑到断点处，才真正开始执行计算，从而实现逻辑上的“断点续传”
    // 原生方法
const localSetTimeout = typeof setTimeout === 'function' ? setTimeout : null;
const localClearTimeout =
  typeof clearTimeout === 'function' ? clearTimeout : null;
const localSetImmediate =
  typeof setImmediate !== 'undefined' ? setImmediate : null;

// 安排切片任务的方法
let schedulePerformWorkUntilDeadline;

if (typeof localSetImmediate === "function") {
  // Node.js / 老 IE 优先用 setImmediate
  schedulePerformWorkUntilDeadline = () => localSetImmediate(performWorkUntilDeadline);
} 
else if (typeof MessageChannel !== "undefined") {
  // 浏览器环境 → 使用 MessageChannel（这是最常见情况）
  const channel = new MessageChannel();
  const port = channel.port2;                    // 发送端

  channel.port1.onmessage = performWorkUntilDeadline;   // 接收端绑定回调

  schedulePerformWorkUntilDeadline = () => {
    port.postMessage(null);   // ← 关键！触发异步任务
  };
} 
else {
  // 兜底：setTimeout
  schedulePerformWorkUntilDeadline = () => {
    localSetTimeout(performWorkUntilDeadline, 0);
  }
}

// 运行切片任务的方法
const performWorkUntilDeadline = () => {
  if (enableRequestPaint) {
    needsPaint = false;
  }
  if (isMessageLoopRunning) {
    const currentTime = getCurrentTime();
    // Keep track of the start time so we can measure how long the main thread
    // has been blocked.
    startTime = currentTime;

    // If a scheduler task throws, exit the current browser task so the
    // error can be observed.
    //
    // Intentionally not using a try-catch, since that makes some debugging
    // techniques harder. Instead, if `flushWork` errors, then `hasMoreWork` will
    // remain true, and we'll continue the work loop.
    let hasMoreWork = true;
    try {
      hasMoreWork = flushWork(currentTime);
    } finally {
      if (hasMoreWork) {
        // If there's more work, schedule the next message event at the end
        // of the preceding one.
        schedulePerformWorkUntilDeadline();
      } else {
        isMessageLoopRunning = false;
      }
    }
  }
};
